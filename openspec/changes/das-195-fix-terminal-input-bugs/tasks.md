- 4.2 (Release) left open: it runs after merge (tag `v0.1.1` on main), so it cannot be done from this branch.
- 2.1 (Backend): `TerminalSession` drops `framePending`/`requestFrame`. The reader counts each chunk in `unfedChunks` before queueing its feed; the feed task decrements it and publishes when it reaches 0, so the terminal thread publishes once no read chunk is still unfed (design D1). A burst still gives one frame, and the last feed of a burst always publishes. The decrement runs before `terminal.feed`, so a feed that throws cannot leave the count stuck above 0 and stop all later frames.
- 2.2 (Backend): a first test with only fast output (`yes | head -n 200000`, then the marker) passed against the old code: the terminal thread kept up and the race did not occur. The kept test makes the terminal thread busy with a frame sink that sleeps 300 ms, while the program writes 8 chunks 50 ms apart, then `END-OF-BURST`, then blocks on `read`, so later chunks queue behind a publish by timing rather than by luck. Against the old code it failed, the last frame ending at `chunk 7`; after 2.1 it passed 4 runs in a row.
- 1.1 (Frontend Components): `TerminalCanvas.paintRow` draws a batched ASCII run through `drawOnGrid`, one `GlyphVector` per run with each glyph positioned at `i * cellWidth` (one reused `Point2D.Float`), so the run stays one draw call (design D2). Single cells that are not ASCII, box-drawing stretches and the block caret's glyph keep `drawString`: each already draws one grapheme at its own cell's left edge, and a `GlyphVector` without shaping would split a combining sequence across cells. The `monospace` field is gone: it only kept proportional fonts out of batches because `drawString` advanced them off the grid; with explicit positions a batch draws them exactly as per-cell drawing did.
- 1.2 (Frontend Components): `TerminalCanvasTest` paints one row at 2x scale into a `BufferedImage` (the Retina case), with `Font.MONOSPACED` at a size whose advance is 0.3 to 0.45 px past a whole pixel, so the advance differs from the whole-pixel cell width whether the IDE's fractional-metrics hint resolves on or off in the test JVM. Row: spaces with `|` at column 50, one batched run; plain and bold. Against the old batching both failed (ink at device x 637..639 plain and 667..670 bold, cell 600 until 612); after 1.1 both pass. No logging added: the paint path runs per frame and has no failure branch worth a log.
- 3.1 (Frontend): reproduced on 2026-09-30 in the sandbox (IU 2026.1.2, keymap "Mac OS X 10.5+"), panel focused, `cat -v` in the pane, real CGEvent keys, with a temporary `info` log in the fallback's press, typed and release handlers. Cmd+comma: Settings opened, and the fallback got the press unconsumed (`keyCode=44 modifiersEx=256 consumed=false`, keymap actions for the stroke `[ShowSettings]`) and then the release; no typed event. The press was sent through the encoder and `cat -v` showed `,`. The IDE's key dispatcher skips `ShowSettings` because its `update` disables it on macOS for any input event (`ActionPlaces.isMacSystemMenuAction`): the macOS app menu runs Settings natively, which is D5's inferred cause. Cmd+O without the prefix: Go to Class opened and the fallback saw nothing, so the IDE's dispatcher consumed it. `ctrl+;` then Cmd+O: nothing opened and the fallback saw nothing, because the router claimed Cmd+O for Herdr (D4's cause). The cause matches the design; the log is removed.
- 3.2 (Frontend): `TerminalKeyFallback` takes an `ideHandles` check and sends nothing for a press it reports; the typed event and release then send nothing either, because the press never becomes the pending typing press and never enters `pressed`. The check is the new `terminal/shared/services/IdeKeyActions`: the active keymap's action ids for the press's keystroke, each updated in the panel's data context (place `KEYBOARD_SHORTCUT`), true when one is enabled; a non-dumb-aware action counts as disabled in dumb mode, as in the IDE's key dispatcher. Surprise: the first build updated the actions with the key event and still sent `,` 10 of 10 times, because `ShowSettings` disables itself on macOS for any input event. The update now runs without the key event, so an app-menu action counts as enabled. Risk: an action whose `update` otherwise depends on the input event could answer differently than it does for the IDE's dispatcher; none was seen in the checks. Wired in `HerdrPanelView` with `IdeKeyActions::handles`. Sandbox check (5.7's steps): Cmd+comma opened Settings 10 of 10 times and `cat -v` showed nothing; typing, Enter, Left and Backspace still reached `cat -v`.
- 3.3 and 3.4 (Frontend), one commit because both change the fallback's constructor and its wiring in `HerdrPanelView`: `TerminalKeyFallback` takes `isMac` and `onText`. On macOS a press whose modifiers are exactly command, on left, right or backspace, sends `\u0001`, `\u0005` or `\u0015` to `onText` and is consumed; a repeat is another press, so it sends again, and the release is not in `pressed`, so it sends nothing. The IDE check from 3.2 runs first, so a keymap binding on one of these chords still wins; the default macOS keymap binds none of them in the panel (the sandbox check below reached the pane). Linux and any other modifier set keep the encoder. Raw path: `onText` → `HerdrPanelViewModel.input` → a new named action `herdr.terminal.input` (argument `text`, so the action server can drive it too) → `HerdrClient.input` → `TerminalSession.input`, which writes the UTF-8 bytes to the pty on the terminal thread and never calls the key encoder. `HerdrPanelView` passes `SystemInfo.isMac`. Sandbox check (5.5's steps), `stty -icanon; cat -v` in the pane: Cmd+Left, Cmd+Right and Cmd+Backspace showed `^A ^E ^U`, each once; Cmd+Shift+Left showed the encoded `^[[1;10D`. At a zsh prompt, `echo hello` then Cmd+Left, a key, Cmd+Right, a key put the keys at the line's start and end, and Cmd+Backspace cleared the line.
- 3.5 (Frontend): `HerdrKeyClaims.route(stroke, keymap)` replaces the public `claim` and returns the new `herdr/shared/models/HerdrKeyRoute` (`claim` plus `closesPrefix`). While the prefix is pending, the next key clears it; a key Herdr binds after the prefix, the prefix key or Esc routes to Herdr; any other key, including one Herdr cannot bind, gets `closesPrefix = true` and the claim it would get with no prefix pending, so an unbound chord goes to the IDE and a direct Herdr binding still goes to Herdr. `HerdrKeyRouter` sends an Esc press and release to Herdr when `closesPrefix` is set, then applies the claim as before; Herdr closes prefix mode on Esc without forwarding it, so the pane gets nothing from the Esc. Docs on `HerdrKeyClaims`, `HerdrKeyRouter` and the `HerdrKeyClaim` enum now point at ADR-0004. `HerdrKeyClaimsTest` moved to `route` in this commit, so the commit compiles on its own; its new outcome tests are 3.6's. Sandbox check (5.6's steps): `ctrl+;` showed Herdr's PREFIX bar, then `v` split the pane; `ctrl+;` then Cmd+O opened the IDE's Go to Class popup, the PREFIX bar went away, and a later `v` typed `v` in `cat -v`; `ctrl+;` then `y` (unbound after the prefix) closed the PREFIX bar and typed `y`.
- 3.6 (Frontend): `HerdrKeyClaimsTest` drops the old "the next key is one the IDE binds, then Herdr still gets it once" test, which pinned the behaviour 3.5 replaces, and adds the follow-up outcomes against the fixture: `prefix+v` bound, the prefix twice, Esc, then for Cmd+O, plain `y`, a non-bindable key, Cmd+K (a direct Herdr binding) and Cmd+C (copy) the no-prefix route plus `closesPrefix`; each case checks that a plain `v` after it goes to the IDE, so the pending state is cleared. The new `TerminalKeyFallbackTest` drives the listener with synthetic `KeyEvent`s: the three macOS chords send their byte on press and repeat and nothing on release, Linux `super+left` sends the encoded press and release, other modifier sets and a plain arrow stay encoded, and a press the IDE handles sends nothing for its press, typed event and release. `./gradlew test --tests '*HerdrKeyClaimsTest*' --tests '*TerminalKeyFallbackTest*'`: 8 and 4 tests, no failures.
